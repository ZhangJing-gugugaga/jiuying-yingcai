## 综合验收与继续执行顺序

1. 冻结原 ZIP 与源码提交。基线测试、重现问题及小范围回归。确定有影响的页面与 API 调用方。
2. 公众查境外网点后登录、三网点修改退回月报、月度核验、费用原账单与退款回读、普通咨询转主动正式工单、停业与独立停费。旧培训补件路径继续做兼容回归。
3. 核验总部角色入口、五个筛选缺陷、空态、账期和导出范围，检查过往审批与审计。业务规则待确认单独记录。
4. 回归 Node、全量总部 Chrome、官方微信编译、原生路由、部署隔离和迁移恢复。尽可能在同源码的微信模拟器走界面。实际无法运行时记录可核查原因。继续复查开放项并修复可复现回归。
5. 最终交付本执行包、功能矩阵、独立源码 ZIP、SHA256、实际验收及余项。准入以证据判断。无正式商户调用、无正式平台发布。

## 整合时复现并修正的三条路径

| 现象 | 处理 | 复验证据 |
| --- | --- | --- |
| 网点分页能清除已失效网点的费用或协议访问提示 | 分页后的费用和协议加载继续核验当前网点。无权限时保持错误和原选择，可以另选有权网点。 | 超过 50 个网点的隔离 SQLite 场景。费用和协议列表未发出无权查询，重选本人网点恢复。 |
| 切换网点后仍显示先前付款结果或待确认订单 | 网点或账期变化时清空本页付款提示，原订单、账单和实收继续保存。 | 隔离 Mock 入账一次，切换网点后旧提示消失，原实收仍可查询。 |
| 作为入口的「联系总部」可能继承上一次通知携带的工单路径 | 通用客服导航明确进入首屏，带业务 ID 的深链仍精确打开原工单。 | Node 原生导航事件测试，旧通知返回、直接联系客服和登录场景均复验。 |
