## 迁移 020/021、备份与恢复

从 SQL 001–019 合成旧库，放入已入账订单与实收、待处理退款、总部月报待办及一条审计。先用 SQLite 一致性快照固化 019 库，再用项目 CLI 连续升级两次。两次的 21 条迁移登记及业务检查一致。独立用例另覆盖旧通知定位、过期待办保留、加盟商待办稳定及跨主体隔离。

- **020** 保留历史实收 12,345 分、原渠道确认号和空的旧环境标记。待退款 1,101 分仍为 pending，查询计数初始化为 0，回填了原请求方和幂等键。
- **021** 保留总部待办原始 JSON，为相应加盟商生成一条可处理待办。第二次迁移保留首次创建的待办 ID。
- 019 快照可校验，升级后用现有 CLI 完成备份、校验和恢复到全新路径。恢复前后快照 SHA256 一致，integrity_check 为 ok，外键违规数为 0，一条审计的链头保持一致。再次恢复到已有路径按预期退出 1，原恢复文件 SHA256 不变。
- 发布应停写并序列执行单个迁移进程。当前迁移登记在取得写锁前检查，连续重复通过只证明串行幂等。备份的 create 会通过 openStore 打开源库并执行缺失迁移。生产升级前应使用在旧版本验证过的一致性快照流程，保留独立 SHA256、所需解密密钥与异地副本。生产演练须明确停写窗口、恢复点和恢复时间，核对账务、任务、通知、副作用及旧版应用读取兼容。迁移后新增支付与消息应对账并补偿，回退前先停新版 worker。

## 容量、成本与上线资料

两组均为本机内存 SQLite、8 并发、120 次读取、0 失败。10,000 条历史月报场景测得 p50/p95 85/120 ms，3,600 条当前加 3,600 条历史任务场景测得 266/295 ms。已观察到部署使用同步 SQLite、WAL、单写者和 5 秒 busy timeout。每个 HTTP 完成事件还写运行计数，因此容量验证需覆盖真实磁盘、混合读写、图片 BLOB、长周期留存、备份窗口和后台作业争用。当前数据可作为本机基线，目标并发、容量和服务指标待压测确认。

专项未引入运行依赖或调用计费平台。正式服务器磁盘、附件、监控、异地备份及外部平台预算由实际数据规模和业务量核定。
