## 1. 从 GitHub 接手

从[项目主分支](https://github.com/ZhangJing-gugugaga/jiuying-yingcai/tree/main)获取整理后的工程。安装依赖前确认 Node.js 版本为 `>=24.19.0 <25`。

```powershell
git clone --branch main --single-branch https://github.com/ZhangJing-gugugaga/jiuying-yingcai.git
Set-Location jiuying-yingcai
git rev-parse HEAD
npm ci
Copy-Item .env.example .env
powershell -NoProfile -File .\start.ps1
```

上游源码快照的提交为 `bdc8e8b58864de7de4ade8494f25603ca0d29c6e`。本仓库从快照导入，上述 git rev-parse HEAD 输出本仓库的提交号。接手包中的代码按此提交核验，方便离线阅读。开发使用分支。测试数据、生成构建和配置密钥放各自受控环境。 [源码与本地运行](03-源码与本地运行.md)

## 2. 三方如何完成同一件事

总部 Web 菜单会随岗位收窄。以下名称对应实际工作区导航。需要个人操作时使用在本测试库激活的账号。分派、改派、提交人与复核人独立等用例使用不同的个人身份。

| 业务 | 加盟商负责人 | 一级管理员 | 总管理员 | 必验结果和关键接口 |
| --- | --- | --- | --- | --- |
| 首次开通与换绑 | 首次激活后登录，从「我的 → 账号安全」发起负责人或登记手机号申请 | 按已获授权看必要业务，不使用其他人凭证处理 | 「网点与账号 → 账号与授权」创建主体、开通/签发激活、审核变更 | `/api/auth/activation`、`/api/auth/activate`、`/api/auth/password` 归属同一账号。旧会话失效，新负责人仍关联原主体的网点和历史 |
| 普通月报 | 「月报」选网点月，存草稿并报送，退回后查看原因并重提 | 运营从「业务待办/经营月报」查看原版本，按规则审核或退回。区域岗需额外获该网点审核权 | 可查看审核及原始审计，在相应权限内处理普通运营审批 | `/api/reports/context` 返回对象范围，`report.draft`、`report.submit`、`review.report`。草稿与提交版分开，退回重提生成新版本 |
| 历史收入更正 | 从当前有效月报选择更正范围和原因，提交新版本 | 运营初审后，财务复核涉及的收入变化 | 复核通过后从经营看板或重结算待办统一结算。误审需要撤销时发起复核 | `report.correct`、`review.report`、`report.revoke.request`、`review.revoke`、`settle`。对照当前有效、最新提交、正式结算三个状态 |
| 网点新增、状态与位置 | 从办理事项申请新增、状态变更或地址变化；原单补交材料。每月核验从工作台或我的事项办理 | 位置岗核验私有证据，运营处理适用的申请及营业状态。首次建档由适用审批完成 | 管理网点档案和公开资料；在有授权的路径处理运营审批 | `request.submit`、`request.supplement`、`location.submit`、`location.review`、`review.request`。核验或创建对象只发生一次，原记录可回查 |
| 协议、应收和实收 | 工作台服务费看原账单，使用允许的付款方式，或从付款与凭证登记等额线下款 | 财务核账单、订单状态、收款凭证及外部流水，完成独立复核 | 设置价格版本和协议，核查集团账务与异常，管理对账流程 | `plan.publish`、`agreement.create`、`billing.generate`、`/api/payments/prepay`、`offline.submit`、`offline.review`。渠道实收成功及财务登记次数须核对 |
| 停费、退款与开票 | 停费从本网点申请，退款和票据以原实收为依据。从原账单查询结果 | 运营可提核算；财务做适用停费审批、独立核算复核、退款及票据状态处理 | 可发起合规的费用核算和账单纠错，管理规则及异常 | `fee.adjust.propose`、`fee.adjust.review`、`refund.request`、`refund.review`、`refund.record`、`invoice.request`、`invoice.update`。业务批准、渠道执行和实际入账分别查证 |

## 3. 状态词和关键保护

| 问题场景 | 以什么为准 | 验收反向用例 |
| --- | --- | --- |
| 月报已经通过，首页暂未出数 | 月报的当前有效版本供过程统计，正式展示取有效结算快照。已有快照因历史变更而失效时等待重结算 | V1 已结算，发起 V2 更正，分别观察审核中、审批通过待重结算、重结算后的变化 |
| 暂停营业后仍收到收费提醒 | 营业档案按有效日期独立变化，费用走另一业务申请。停费批准后待核算金额为 null | 仅批准停业时账单仍按合同口径，未设金额时不显示 0；批准停费后由独立财务检查抵扣月 |
| 付款后短暂仍待付 | 账单和支付订单分离，渠道事实经服务端核验后入账。前端回执可触发查询 | 用 Mock 或隔离签名夹具模拟丢失回执及重复回调，确认原账单后续可查且只记一次 |
| 点了已读仍有待办 | 通知读状态和业务任务状态独立。业务完成或任务规则判定时闭合 | 读通知后刷新，原待办仍在；完成实际审批或补件后核对待办 |
| 可见列表但原单打不开 | 当前会话、账号状态、记录所属网点、任务责任、字段权限和时间范围共同控制访问 | 用另一加盟商、撤销区域授权的账号和被改派的同岗人员分别打开旧链接 |
| 弱网或返回后发现提交结果未知 | 前端保留提交对象和可重试键。服务端按 `subject + Idempotency-Key` 和请求指纹处理。相同键及内容可确认原结果 | 同键同内容重试，只有一条真实写入；同键换内容触发冲突。不向用户呈现猜测的成功结果 |
| 手动选完地址仍需提交现场定位 | 月度通过要求现场 GPS，地址辅助选点和实地证据的出处不同。恢复草稿须重新确认取证 | 拒绝定位后尝试选点，再恢复文字草稿。用真实停留前后路径确认不会沿用以前网点的证据 |

## 4. 请求排查顺序

1. 在微信工具或浏览器的网络记录里抄下环境、当前角色、路由、网点、月份、记录 ID 和 `requestId`。小程序请求失败时查响应体，下载或回调需要时查 `X-Request-Id`。提交过程不要记录口令、令牌和整段私有资料。
2. 匹配服务端日志和授权审计。开发时可通过 `REQUEST_LOG=1` 输出路径、请求号、耗时和状态。检查账号启用、主体归属、区域授权、岗位、任务归属及授权有效期。
3. 核对对应命令、传入对象 ID 和动作以前的真实状态。用 `/api/context`、授权集合详情、待办、审批历史或财务详情核对。跨环境严格使用各自样本账号和对象编号。
4. 网络失败或 5xx 时先通过原单、回查与审计核对是否已写入。401 要重新登录再回原目标。403/404 先检查授权、发布撤回或对象变化。409 用当时对象和最新状态重现，检查重复提交或并发审批原因。
5. 提交缺陷时附最短复现、应有结果、实际结果、是否影响其他岗位、建库或配置前置和同版本证据。复测后记录首次通过版本和残余限制。

配置与业务制度以受控环境约定为准。微信真实登录、短信、支付、公众号及真实定位需各自验证凭证、域名、渠道和授权。当前材料中的开发登录、测试模拟和替身只服务隔离联调。 [生产准备](../../docs/上线资料清单.md) · [V4.1 证据](验收证据/V4.1原始综合验收报告.md)
