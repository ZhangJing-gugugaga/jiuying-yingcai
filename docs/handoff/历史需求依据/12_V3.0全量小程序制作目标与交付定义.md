# 九盈英才 V3.0｜全量小程序制作目标与交付定义

## 1. 本次纠正：交付目标是什么

用户要求制作的是**完整的微信原生小程序产品及其支撑系统**，不是只制作HTML演示原型。

本轮Codex的首要任务是交付可运行、可调试、可测试的完整项目代码。HTML原型只作为既有交互参考和需求验证材料，不再作为主要交付物，不得把“完善HTML”当作完成本项目。

完整业务闭环必须由以下部分组成：

1. 微信原生小程序前端：加盟商负责人日常使用为主，必要的消费者公开入口与客服入口保留。
2. 服务端API和业务逻辑：账号、加盟商、网点、月报、账单、支付状态、地图核验、客服工单、经营看板、消息、审批和审计。
3. 数据库：结构化保存业务实体、状态、版本、关联、操作记录和权限。
4. 总部管理后台（Web）：总部账号、加盟商、网点、月报审批、服务费、位置核验、客服工单、经营汇总、授权、内容管理、导出和审计。
5. 外部服务集成层：微信登录/身份、微信支付、微信订阅消息、地图与定位、文件上传等，采用可替换适配器。
6. 测试、部署和运维材料：本地开发环境、数据库迁移、种子数据、自动化测试、配置说明、接口文档和部署手册。

当前项目范围是**完整微信小程序及支撑它的后端和总部Web管理端**。iOS/Android独立APP暂不属于本轮交付；公众官网也不属于本轮交付。消费者端保留必要的小程序公开网点查询与客服入口，但产品主线仍是加盟商。

## 2. “完整制作”的完成定义

“完整”指核心业务能通过真实项目代码在本地开发环境跑通，而非每个功能只有页面。

至少达到：
- 小程序可以启动、路由、表单交互、上传演示附件、展示状态和调用真实本地API。
- 后端服务可启动，提供真实业务API、参数校验、错误处理、权限检查和业务事务。
- 数据库可通过迁移脚本从空库初始化，具备演示种子数据。
- 总部Web管理端可以登录测试账号，完成审批、网点、客服、服务费、看板和权限操作。
- 小程序与总部后台读写同一套后端和数据库；同一条申请在两端看到一致状态。
- 月报版本、账单、支付订单、费用调整、GPS核验、工单和审计记录有明确数据模型。
- 关键业务流程有自动化/API/端到端测试。
- 所有外部真实凭证未提供的功能，采用明确的开发/模拟适配器，保留真实集成接口与配置说明；不得伪称真实交易已完成。
- 可以使用本地开发账号和种子数据完整演示，不依赖甲方生产账号。

## 3. 技术路线

### 3.1 先检查现有仓库
如果项目目录已有原生小程序、后端或管理后台工程，先检查并优先延续合理的技术栈，禁止为了追求统一而无理由推翻现有可用工程。

如果没有可复用工程，采用以下默认建议：
- 微信小程序：原生微信小程序 + TypeScript（如当前工具链不支持TypeScript，可采用原生JS，但保持模块化）。
- 后端：Node.js LTS + TypeScript + NestJS（或仓库已有成熟后端框架）。
- 数据库：PostgreSQL；使用Prisma或同等迁移工具。
- 总部Web管理端：Vue 3 + TypeScript + Vite + Element Plus（如已有成熟管理端则沿用）。
- API规范：REST JSON，统一错误码、分页、过滤、鉴权和审计字段；生成OpenAPI/Swagger文档。
- 本地开发：Docker Compose启动数据库及必要依赖；不强制Redis，只有真实需要才加入。
- 测试：后端单元/集成测试，小程序关键页面/业务测试，管理后台关键流程测试；有浏览器自动化能力时增加E2E。

技术栈可因现有仓库、Codex环境和兼容性调整，但必须记录理由，保证前后端可运行和交付可复现。不得仅输出架构图而不落代码。

### 3.2 微信原生要求
- 必须创建可由微信开发者工具识别的原生小程序项目结构，如 `miniprogram/`、`app.json`、`app.ts/js`、页面 `wxml/wxss/ts/js`、组件和配置。
- 不能用一个H5网页嵌入WebView冒充原生小程序。
- 不能把之前HTML文件重命名为小程序源码。
- 配置 `project.config.json`、页面路由、分包（确有必要时）、权限声明和开发环境配置。
- 提供无真实AppID时可使用测试/游客开发模式；正式微信登录需配置AppID和服务端凭证。
- 微信支付必须通过后端下单和支付结果验签/回调流程；无商户号时只启用Mock支付适配器。
- 订阅消息无模板ID时启用站内消息/Mock通知，不伪造真实推送。

### 3.3 地图和高德
- 用户表示已接入高德地图MCP/CCDB。先检查Codex当前会话可见的MCP工具。MCP主要用于开发时查询/辅助，不等于运行时小程序地图服务。
- 小程序运行时优先采用微信定位能力（用户主动授权）和高德地图官方适配方案；需要的Key、服务白名单、微信小程序插件或API配置由环境变量/配置文件占位，不得硬编码密钥。
- 如无法接入真实高德服务，仍须完成地图组件、手动选点、地址字段、定位权限处理、模拟坐标和适配器接口；明确标记Mock。
- 不得后台持续定位；每月核验由加盟商主动进入页面并点击定位，提交GPS、地址和现场照片。

### 3.4 安全
- 密码/会话、微信身份、RBAC、数据范围校验由服务端执行。
- 不得仅靠前端隐藏按钮实现权限。
- 关键写操作需事务、幂等键/重复请求保护、审计日志。
- 上传文件进行类型/大小校验，限制访问权限。
- 消费者投诉信息最小化共享；客服默认无经营/财务数据权限。
- 真实密钥只从环境变量读取，提供 `.env.example`，禁止提交真实凭证。
- 开发环境Mock账号与生产配置严格隔离。

## 4. 必须建设的核心领域模块

### 4.1 身份与组织
- 总部创建加盟商主体和唯一负责人账号。
- 一个负责人管理多个网点。
- 登录入口保留微信和手机号；正式微信登录凭证缺失时用开发账号模式。
- 账号激活、冻结、恢复、停用、负责人换绑、手机号变更、微信解绑、管理员离职待办交接。
- 第一阶段不增加店长/财务子账号，不开放加盟商自主创建内部账号。
- 总部、总部管理层、运营审核、财务复核、位置核验、客服、区域运营等岗位权限按基线执行。

### 4.2 网点
- 新增网点申请、总部审批、筹备中建档、开业确认、营业中、暂停营业、恢复、关闭。
- 网点字段至少覆盖名称、主体/负责人关联、省市区县、详细地址、联系电话、预计开业日、经营说明、附件状态、地图位置。
- 每个网点有稳定唯一ID，申请审批通过只能创建一次，重复点击不能重复建档。
- 状态变更保留生效日期、操作人、原因和历史。
- 网点转让、重开和历史责任待定，采用待确认处理，不自行推导。

### 4.3 经营月报与更正
- 每网点每自然月一份当前有效正式汇总，允许版本历史。
- 每月1—5日填报上月，总部6—10日审核；逾期仍可补报并标记。
- 五项指标：财务确认营业收入、完成有效订单、到店客流人次、实际招生人数、不适用状态/经营说明。
- 草稿、提交、待审核、退回、重新提交、通过、逾期、免报、更正等状态独立。
- 只有通过版本进入正式经营统计。
- 退回重报保留版本；加盟商只看当前有效报表和历史处理摘要；总部看完整审计。
- 已审核月报更正由加盟商发起，总部审核；涉及收入增加财务复核。
- 总部误审批由高级管理员发起纠正/撤销并复核。
- 总部可以调整统计汇总层，但不能修改加盟商原始月报，记录前后值、原因、操作人。
- 整月免报与0值报表分开；整月停业发生财务事项的处理待集团决定。

### 4.4 经营看板
- 加盟商只看本人网点，首页本人全部网点汇总，可查看单店详情。
- 首页四项指标：收入、订单、客流、招生。
- 月/季/年汇总、趋势、同比/环比、本人网点对比。
- 默认当月；环比上月，同比上年同月。
- 总部全集团/加盟商/网点汇总。
- 四项分别排名，仅总部管理层查看，不设综合排名。
- 区域运营按指标和网点逐项授权。
- 正式数据每月统一结算后更新；过程数据与已结算数据分开。
- 异常包括逾期未报、指标明显异常、长期无经营数据，站内消息通知。
- 加盟商导出本人全部网点数据；总部导出仅管理层。
- 月度报告包括指标、趋势、排名、异常和经营说明；加盟商不得看到集团排名。
- 历史经营数据至少保留5年。

### 4.5 服务费和支付
- 每网点自然月独立咨询服务费账单。
- 应收账单与支付订单、实收流水分开。
- 未支付也生成应收。
- 历史三档1980/4800/9800元仅为暂定示例，不得视为正式定价；套餐、服务内容、账单日、缴费截止日待定。
- 暂停营业不自动停费；暂停收费申请由加盟商发起，总部审批。
- 已付未享受服务原则上优先顺延，特殊退款另行审批；算法未定只显示待核算调整。
- 真实支付未配置商户号时使用Mock支付，真实支付适配器必须服务端下单、验签回调、幂等防重。
- 账单、支付、退款、发票、线下付款和费用调整记录分层；未确认规则不擅自落地为正式计算。

### 4.6 地图与位置核验
- 新增网点地图选址和总部核验。
- 每月核验；系统提醒，加盟商主动提交GPS、地址、现场照片。
- 总部专门位置核验人员审核。
- 偏差阈值待定；超阈值标异常，逾期标异常由总部人工处理。
- 不一致要求解释和证明；位置变更另行申请、总部审批。
- 公众仅看普通网点地址和普通地图标记；精确GPS及核验记录仅加盟商和总部。
- 定位采集方式尚待确认；可实现主动定位与手动选点适配器，但标注规则待定。
- 不允许后台持续定位。

### 4.7 全渠道客服
- 消费者公众号/小程序，加盟商小程序在线/电话。
- FAQ自动回复＋人工；用户选择是否转人工。
- 普通咨询只保留聊天记录；投诉、售后、业务异常生成正式工单。
- 统一工单队列，客服自助接单。
- 总部客服始终负责工单，内部协作不转移负责人。
- 消费者投诉由总部客服直接处理，所有消费者投诉通知加盟商；仅共享必要信息。
- 严重投诉升级总部高级管理层。
- 客服默认无经营/财务数据访问权，需要时总部授权。
- 服务时间总部设置；首次响应SLA按工单类型配置。
- 客服标记完成即可关闭；未解决则新建关联工单。
- 仅评价人工客服。
- 客服不能代替正式业务审批。

### 4.8 消息与待办
- 消息与业务待办分开建模。
- 已读不等于业务完成。
- 待办关联具体网点、月份、账单、申请或工单。
- 覆盖月报提醒、审核退回/通过、网点审批、账单到期、支付确认、停费结果、位置核验、客服回复。
- 真实短信/公众号订阅消息未配置时使用站内消息Mock。

### 4.9 总部Web管理端
必须建设与小程序共用同一后端和数据库的总部管理端，至少覆盖：
- 登录与角色权限；
- 加盟商主体和负责人账号；
- 网点档案、状态、位置核验和变更审批；
- 月报审核、更正和总部纠错；
- 服务费账单、支付状态、暂停收费和待核算调整；
- 客服统一队列、接单、协作、投诉通知和升级；
- 经营汇总、排名、异常、Excel/PDF导出；
- 区域运营授权；
- 公开内容/网点资料维护；
- 审计日志和操作记录。
总部管理端是完成业务闭环的必要部分，不可只做手机端模拟切换代替。

## 5. 实施阶段

### Phase 0：资产审计与项目启动
- 阅读全部项目包文件和原始交接ZIP。
- 检查当前仓库、工具、环境、Node/Python/微信开发工具可用情况。
- 建立执行日志、检查点和风险日志。
- 对原型和现有代码备份。
- 产出系统架构决策记录、模块清单和数据关系草图。
- 不能只输出分析后停止，继续实现。

### Phase 1：工程骨架
- 创建原生微信小程序工程。
- 创建后端工程和数据库迁移。
- 创建总部Web管理端。
- 配置共享API类型/接口文档。
- Docker Compose或等价方式可启动本地数据库和后端。
- 提供 `.env.example`、README、开发账号/种子数据。
- 完成登录Mock和角色切换的开发环境模式。

### Phase 2：领域数据模型与API
至少建立：
- organizations/franchisees
- users/identities/roles/permissions
- stores/store_status_history/store_location_versions
- location_verifications/location_evidence
- monthly_reports/report_versions/report_reviews/report_corrections
- service_agreements/plan_versions（未确定字段可留空/待配置）
- invoices/payment_orders/payment_transactions/refunds/fee_adjustments
- support_conversations/support_tickets/ticket_messages/ticket_assignments/ticket_links
- notifications/business_tasks
- operating_statistics/statistic_adjustments
- audit_logs
- content_pages/public_store_profiles
模型命名可按技术栈调整，但实体关系和业务边界必须保留。

### Phase 3：小程序核心功能
实现真正的原生页面、组件、导航、表单校验、状态反馈和API调用：
- 登录/账号激活（开发Mock）
- 加盟商工作台、多网点切换
- 我的网点、详情、状态、地图位置
- 月报列表、填报、草稿、提交、退回、重报、历史摘要、更正申请
- 服务费账单、支付订单、支付结果、暂停收费申请
- 业务申请、待办、消息
- 地图月度核验、现场照片上传、异常解释、位置变更申请
- 客服FAQ、聊天、转人工、电话入口、工单、历史和评价
- 经营看板、趋势、同比环比、网点对比、导出
- 个人资料、账号安全、退出登录
- 公众普通网点列表/地图和消费者客服入口（保留但不作为主线）

### Phase 4：总部Web管理端
实现真实管理操作，不只是页面：
- 账号与加盟商管理
- 网点审批和位置核验
- 月报审核和历史更正
- 账单、支付、暂停收费、待核算调整
- 客服统一队列与投诉管理
- 经营统计、排名、导出
- 区域权限配置
- 内容维护
- 审计日志

### Phase 5：跨端业务闭环
至少实现并测试：
1. 总部创建加盟商与负责人 → 加盟商登录 → 看到多网点。
2. 新增网点 → 地图选址 → 总部审批 → 网点建档。
3. 月报提交V1 → 总部退回 → V2重报 → 审核通过 → 统计更新。
4. 月度GPS核验提醒 → 主动定位/上传照片 → 总部审核 → 异常/通过。
5. 服务费应收 → 支付Mock/真实适配器 → 结果同步；暂停收费 → 待核算调整。
6. 消费者/加盟商客服 → FAQ → 转人工 → 工单 → 总部接单 → 协作 → 关闭/关联工单。
7. 经营看板 → 汇总/排名/导出权限。
8. 业务消息与待办随业务状态变化。
9. 总部/区域/加盟商数据权限隔离。
10. 网点暂停、整月免报、关闭等生命周期状态不破坏历史记录。

### Phase 6：测试与安全
- 数据库迁移从空库可执行。
- 种子数据可重置。
- API鉴权和数据范围检查。
- 角色越权测试。
- 重复提交、重复审批、支付幂等测试。
- 月报版本与统计一致性测试。
- 服务费账单与支付记录一致性测试。
- 客服隐私和工单权限测试。
- 地图定位拒绝/失败和附件上传测试。
- 微信开发者工具编译（如果环境可用）；否则记录未能使用微信工具的限制。
- 后端单元/集成测试，前端关键流程测试，管理端E2E尽可能完成。
- 不得仅凭静态代码检查宣称完成。

### Phase 7：交付和文档
交付完整可编辑项目：
- `miniprogram/`：微信原生小程序源码。
- `server/` 或等价后端源码。
- `admin-web/`：总部Web管理端。
- `database/`：迁移、种子数据和数据字典。
- `docs/`：架构、业务流程、API、权限矩阵、部署、测试和待确认事项。
- `.env.example`：所有外部配置占位，不含真实密钥。
- `docker-compose.yml` 或可复现本地启动方式。

## 7. 不要犯的错误

- 不要只做一个HTML，不要只做高保真UI，不要只输出PRD。
- 不要用WebView包装H5冒充微信原生小程序。
- 不要只有小程序前端而没有后端和数据库。
- 不要只有总部后台页面而没有真实API和状态联动。
- 不要把角色切换按钮当成真实权限系统；服务端必须校验。
- 不要让所有按钮都只弹Toast。
- 不要用固定假数据冒充API返回；Mock数据也必须通过统一数据服务层管理。
- 不要在客户端计算并确认真实支付成功。
- 不要后台持续GPS定位。
- 不要将消费者投诉个人信息无差别共享给加盟商。
- 不要覆盖原始月报、账单、支付和审计历史。

- 不要把iOS/Android独立APP扩展进本轮，除非原始需求明确要求本轮交付。
- 不要因缺少AppID、支付商户号或地图Key而停止所有开发。
